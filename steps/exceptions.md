# 예외 상황 프롬프트

상황이 생기면 해당 블록을 복사해 Codex에게 보낸다. `<...>`만 채운다.

## 담당자가 새 요구를 꺼냈다

```
담당자의 새 요구 원문: <원문>
INTERVIEW.md에 원문을 기록하고, DECISIONS.md와 과제 README를 기준으로 판단해 줘.
1. README 필수인가, 2. 없으면 핵심 문제가 안 풀리는가, 3. 포함하면 무엇을 줄여야 하는가.
포함 / 범위 밖 중 추천과 이유를 두 줄로 보여 줘. 내가 정하기 전에는 파일을 고치지 마.
범위 밖이면 담당자에게 보낼 문장도 개발 용어 없이 써 줘.
```

## 담당자의 답이 모호하다

```
담당자의 답 원문: <원문>
이 답으로 정해지지 않은 점만 골라, 선택지 2개를 붙인 질문 하나로 다시 써 줘. 개발 용어와 추천 답은 빼.
같은 항목을 이미 다시 물었다면 묻지 말고, 선택지 2개와 추천을 나에게 보여 줘. 내가 고르면 DECISIONS.md에 응시자 결정으로 남겨.
```

## 담당자의 숫자가 데이터와 다르다

```
담당자가 말한 기준: <원문>
데이터와 대조해 어긋나는 수치와 계산 방법을 보여 줘.
"꼭 지켜야 하는 기준인지, 가능하면 지키고 싶은 기준인지" 묻는 문장을 수치와 함께 개발 용어 없이 써 줘.
답을 받기 전에는 제약으로 넣지 마.
```

## 담당자가 답하지 않는다

```
담당자가 5분째 답하지 않아. 질문: <질문>
추천안으로 진행하고 DECISIONS.md에 상태를 가정으로 남겨. 틀렸을 때의 영향과 나중에 바꿀 곳을 한 줄씩 적어.
```

## Codex가 질문을 멈추지 않는다

```
인터뷰는 여기서 끝낸다. 더 묻지 마.
남은 질문은 [미확인] 또는 가정으로 정리하고, 결과를 가장 바꾸는 항목 3개만 알려 줘.
```

## Codex가 설계나 방법을 앞서 정했다

```
방금 정한 <내용>을 되돌려. 아직 정하지 않은 결정이야.
선택지 2~3개, 입력 규모 근거, 각 약점만 보여 줘. 결정은 내가 한다.
```

## 담당자에게 보낼 문장이 어렵다

```
이 문장을 개발을 모르는 사람이 바로 답할 수 있게 다시 써 줘. 경험이나 선호를 묻고, 추천 답은 넣지 마.
<문장>
```

## 시간이 밀린다

```
지금 T+<분>이고 남은 작업 시간은 <분>이야. 남은 티켓과 시나리오를 필수와 있으면 좋음으로 나눠서, 시간 안에 끝낼 범위를 제안해 줘.
핵심 흐름과 검증 시간을 먼저 지키고, 뺀 항목과 위험을 한 줄씩 적어. 내가 승인하기 전에는 파일을 고치지 마.
```

## 명세와 구현이 어긋났다

```
<어긋난 내용> 때문에 명세대로 구현하기 어렵다. 코드를 고치기 전에 합의, DECISIONS, 명세 중 무엇을 바꿔야 하는지와 영향받는 시나리오를 보여 줘.
담당자에게 물어야 하면 보낼 문장을 개발 용어 없이 써 줘.
```

## 재접속이나 새 세션으로 맥락을 잃었다

```
이전 대화가 없다고 가정해. HANDOFF.md, DECISIONS.md, 현재 티켓, `git log --oneline -10`, `git status`를 읽어.
끝난 것, 진행 중인 것, 다음 할 일 하나를 다섯 줄 안으로 보고해. 내 확인 전에는 파일을 고치지 마.
```

## 미리보기가 열리지 않는다

```
Browser 미리보기에서 서비스가 열리지 않는다. 서버를 직접 띄우지 말고, 코드와 내가 붙여 넣는 터미널 출력을 바탕으로 실제 포트, 0.0.0.0 바인딩, 경로를 순서대로 확인해 줘.
터미널 출력: <출력>
```
