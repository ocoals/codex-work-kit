# 6단계. 구현 (T+75~150, effort medium)

## 목표

필수 티켓이 구현되고 검증된다. 티켓 하나에 세션 하나. 동시에 돌리지 않는다. 한 티켓은 20~25분이 목표다.

## Codex에게

```
$implement docs/<feature>/issues/01-….md
HANDOFF.md와 AGENTS.md를 먼저 읽어.
이 티켓 하나만 구현해. 다른 티켓 파일은 열지 말고, 티켓의 수용 시나리오를 테스트로 먼저 고정해.
테스트, code-review, 커밋까지 끝나면 멈추고 보고해:
1. 실행한 검증 명령과 결과
2. 통과·실패한 시나리오 ID
3. code-review의 Standards / Spec 결과와 처리
4. 명세와 다르게 판단한 점
5. 데이터 흐름과 상태 소유 3줄
```

## 내가 할 것

상황별 처리:

| 상황 | 처리 |
|---|---|
| 명세대로 안 되거나 명세가 틀림 | DECISIONS와 명세를 먼저 고친 뒤 구현 |
| 업무 판단이 필요함 | 담당자에게 현장 말로 묻고 원문 기록. 답이 늦으면 가정으로 표시 |
| 버그로 막힘 | `$diagnosing-bugs`, 먼저 medium으로 한 번 시도. 안 되면 새 세션에서 high로 올림. `docs/AI_LOG.md` 기록 |
| 작은 수정 | 관련 테스트만. 전체 리뷰를 다시 돌리지 않음 |
| 컨텍스트 60% 초과 | `$handoff` 후 새 세션 |
| 티켓 25분 초과 | 멈추고 남은 범위를 나눔 |
| 파일 수정 전에 프롬프트가 잘못됨 | Esc 두 번으로 수정 |
| 파일을 고치기 시작한 뒤 이상함 | Esc로 멈추고 `git status`, `git diff` 확인. 버릴지 정하고 Codex에 알림 |
| 방향만 조금 틀림 | Esc로 멈춘 뒤 정정 메시지 |

핵심 알고리즘 티켓: 단순한 기준선과 결과를 비교해 숫자로 남긴다. 요구 조건 위반 건수를 함께 출력한다. 작은 샘플로 대안과도 비교한다. 결과는 `docs/VERIFICATION.md`에 적는다.

되돌리기: Esc 두 번은 대화만 되돌리고 파일은 그대로일 수 있다. 되돌린 뒤에는 `git status`로 파일을 확인한다. 큰 지시 전에는 커밋한다. 이상하면 바로 멈춘다.

화면의 판단 기준은 `docs/DOMAIN.md`의 To-Be 순서와 담당자 용어다. 디자인은 필수 티켓이 끝나고 시간이 남을 때만 손본다.

## 완료 조건

티켓마다 3분 점검:

- [ ] 실제 실행 결과가 있는가
- [ ] Standards / Spec 리뷰가 돌았는가
- [ ] 다른 티켓까지 구현하지 않았는가
- [ ] 별도 탭의 서버에서 시나리오 하나를 눈으로 확인했는가
- [ ] 화면 순서와 용어가 To-Be와 맞는가
- [ ] 명세와 다른 판단을 승인하거나 고쳤는가
- [ ] 흐름을 내 말로 설명할 수 있는가

## 시간 초과

- T+105: 01·02번이 안 끝났으면 "있으면 좋음" 티켓을 모두 뺀다.
- T+130: 새 기능을 시작하지 않는다.
- T+150: 기능 동결. 동작하는 상태까지만 정리하고 미완성은 한계로 기록한다.
